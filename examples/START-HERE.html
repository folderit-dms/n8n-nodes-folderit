Folderit + n8n: deployment-aware candidate

For testing with connector 0.5.0. This package uses new operations absent from public 0.4.0. Do not replace a working production workflow or assume this candidate is already available on n8n Cloud.

Prepared workflows for Folderit Tailor-plan users with API access. Use your own computer and your own n8n instance. No access to Folderit's development computer is needed.

Start with one small test folder and synthetic documents. These are editable examples; connect and test your own mailbox, Teams and SMTP accounts before activation. No credentials are included.

1. Open n8n

Use the web address supplied by your n8n administrator, or sign up through n8n Cloud. Folderit's own trial instance is not a shared customer service. These workflows do not need Ollama or an AI-provider key. For this candidate, use an isolated self-hosted n8n test instance with the matching 0.5.0 package. Runtime tested: n8n 2.42.5 / Node 24.21.0.

2. Install Folderit and connect it

Have your n8n administrator install the matching 0.5.0 candidate archive in an isolated test instance, using Settings → Community nodes → Install for a registry version when published, or their supported local package installation procedure. Public verified Folderit 0.4.0 does not include deployment connections.

In a Folderit node, set Connection Type → Folderit Connection (Cloud or Custom Deployment). Create a Folderit Connection API credential and enter the API/docs URL, matching client ID and secret, optional exact account UID, and independent browser/sign-in URL. Enter credentials only in that credential dialog. Use a new credential for a different deployment or account.

Save and close the dialog. Select Resource → Connection, Operation → Get, leave Account UID blank and click Execute step. This verifies public routing and the actual account. Initial modal testing cannot perform secure DNS; after this bootstrap read the credential test also works. If several accounts are reported, enter the intended account UID before the first successful connection. No account is chosen just because it is first.

Read the full deployment setup and safety limits. Standard API: https://api.folderit.com; Apollo API: https://api.apollo.folderit.com. A custom deployment must supply its own exact public API and browser addresses. Private/on-premises routing needs a separate supported design.

Start with the read-only deployment check. Enter an existing authorized test file UID and select the SAME Folderit credential in each service node. Execute, inspect the connection and details, then download the output binary and compare its actual bytes with the source. It creates no Folderit record.

3. Create the processing receipt table

Open a blank n8n workflow. In the top workflow menu (⋯), select Import → From file (older versions: Import from File). Choose folderit-ledger-setup.json from this package. Open its Settings node, choose a table name and execute the workflow once. Open Ledger is ready and copy ledgerTableId. Run setup once at a time in the same n8n project as your other workflows.

In the imported workflow's Settings node, replace every YOUR_… value. Paste the table ID from step 3. Select your credentials in every service node and read the yellow notes. In an attachment archive, select the SAME Folderit Connection API credential in Read connection context, Upload attachment, Read uploaded document and Download stored attachment. Keep all copies that should suppress repeats on the same receipt table.

5. Add a failure email

Import Shared failure alerts. Set the real sender, recipient and your HTTPS n8n address, and select an SMTP credential. In each main workflow, open its ⋯ → Settings → Error workflow and choose this saved alert workflow. Test an error in an activated test workflow; manual executions do not automatically trigger failure alerts.

6. Test, then activate

  1. Send one synthetic message with two permitted attachments, or create one synthetic Folderit document after activating the arrival trigger. Confirm the actual destination output.
  2. For expiry reminders, set the document's standard Folderit Due date. Defaults are 30, 7, 1 and 0 days, at 09:00 UTC. The folder scan is not recursive.
  3. Repeat the same input and confirm it produces no duplicate action. Check a controlled failure and its alert.
  4. If a receipt is pending or its lock remains held after a failure, inspect the saved execution and actual destination before retrying. Never simply clear the lock.

Read the complete setup, recovery and validation notes: Customer workflow guide (the same guide is included as CUSTOMER-WORKFLOWS.md).

Upgrade and validation

Preserve your existing receipt table and completed receipts. Standard-cloud keys retain their previous format; custom-deployment keys include the API origin. New actions check their actual credential against the earlier Connection/Get scope before any destination write. A new trigger credential starts a new polling baseline: reconcile outstanding activity first.

The 0.5.0 candidate has local security/regression and native read/download checks. See the exact acceptance evidence and remaining checks. Authenticated Apollo/custom-domain and new-version Cloud acceptance are separate from public discovery.
